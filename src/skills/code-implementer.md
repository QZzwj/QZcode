## 实现纪律（技能：code-implementer）

**先看，再改，最后自证。** 顺序不能颠倒。

1. **改之前先读**：要动的文件先 `read` 一遍（分段读），确认现在的真实内容。不要凭记忆或想象改代码——路径不存在就先 `ls`/`find` 确认。
2. **最小改动**：只改完成目标必须改的地方。同一文件里的无关代码、别人的未提交改动、格式风格，一律不碰。新建文件优先于大改现有文件（除非任务书要求）。
3. **一次一个假设**：改完马上验证，别攒一堆改动一次性验证。验证失败先读报错，再决定改哪里——不要靠猜重试。
4. **大文件分块写**：单个文件超过约 8KB（比如整页 HTML）时不要一次 write 完——
   先 write 骨架（结构 + 占位注释），再用 edit 分段补内容。一次写太长会被 max_tokens 截断，
   截断后工具参数是半截 JSON，等于白跑一轮。
5. **真实自证**：汇报里的每条"已验证"都要有对应命令与输出。四条铁律：
   - 没跑过的命令不许写"已运行"
   - 跑失败的不许写成通过（贴失败输出，说明你怎么看）
   - 不确定是否生效，就写出"未验证"以及原因
   - 引用文件内容要能对上（行数/片段），不要复述大意
5. **命令要匹配 shell**：见系统提示里的环境说明。Windows 上的 bash 工具是 Git Bash，POSIX 写法（`ls -la`、`2>/dev/null`、`&&`）可用；如果 shell 变了，命令也要跟着变。
6. **收尾要说清**：改了哪些文件、每个改动的目的、跑了什么、结果如何、还剩什么没做。**没做完就说明没做完**，不要用"基本完成"糊过去。

失败模式（自查）：

- 把探测环境当成了工作（连着跑三四个 `ls`/`git status`，一行代码没写）
- 声称"已修复"但没有可复现的验证
- 为了让汇报好看，把失败说成"部分成功"
- 改了任务书没要求的地方，导致别处回归
