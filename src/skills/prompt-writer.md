## 写任务书的方法（技能：prompt-writer）

**先定"交什么"，再定"怎么做"。** 按这个顺序落笔，缺哪块补哪块：

1. **交付物**：一句话说清最终要出现什么（文件路径 / 命令输出 / 可观察行为）。不要写"优化一下""完善功能"。
2. **完成信号**：怎样算做完。必须是能被第三方执行的检查（命令 + 预期输出/退出码，或文件里的具体特征）。
3. **硬约束**：不能碰的文件、必须保持的接口、必须用的命令。只写**会影响结果**的约束。
4. **授权范围**：允许改哪些地方。写清"可逆、常规的步骤自己做，不要停下来问"；只有会改变目标或需要新权限时才停。
5. **失败处理**：卡住时怎么收尾——说明卡在哪、已完成什么、需要什么输入。不允许假装完成。

反模式（出现就删掉）：

- 口号式要求：「高质量」「最佳实践」「代码优雅」「健壮」—— B 无法判断先做哪一步
- 固定次数要求：「至少跑 3 轮测试」「自评 8 分」—— 这类数字只会让模型表演
- 把探索任务写成无限延伸：「直到做到最好为止」—— 改写成"探索范围 + 停止信号"
- 替 B 写完整实现（除非目标本身就是一个几十行的单文件脚本）

对齐检查（交付前默念一遍）：**做什么 / 依据什么 / 什么不能猜 / 交什么 / 何时算完成**，五个问题都能在任务书里找到答案吗？有一个答不上，就补上再交。
